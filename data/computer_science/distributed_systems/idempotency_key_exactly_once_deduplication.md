### Idempotency, Idempotency Keys & Deduplication

**Definition:** an operation is idempotent if applying it multiple times produces the same result as applying it once. **`f(f(x)) = f(x)`**.

**Why it matters in distributed systems:** retries are inevitable (network blips, timeouts, redeliveries). Without idempotency, retries cause duplicate side-effects — double charges, duplicate emails, duplicate orders.

**Naturally idempotent vs not:**

| Naturally idempotent ✅ | Not idempotent ❌ |
|---|---|
| HTTP `GET` (no side effects) | HTTP `POST` (creates new resource each time) |
| HTTP `PUT` (replace) | `INSERT INTO orders ...` |
| HTTP `DELETE` (already-deleted = no-op) | Send-an-email |
| Redis `SET key value` | Redis `INCR counter` |
| `INSERT ... ON CONFLICT DO NOTHING` | Plain `INSERT` |
| Absolute update `SET balance = 100` | Relative update `SET balance = balance - 50` |
| Mark-as-paid (already-paid = no-op) | Charge-card (each call charges again) |

**HTTP method semantics (per RFC 9110):**

| Method | Safe (no side effects) | Idempotent |
|---|---|---|
| GET | ✅ | ✅ |
| HEAD | ✅ | ✅ |
| OPTIONS | ✅ | ✅ |
| PUT | ❌ | ✅ |
| DELETE | ❌ | ✅ |
| **POST** | ❌ | ❌ — but can be made so with an idempotency key |
| **PATCH** | ❌ | ❌ — implementation-dependent |

**Five techniques to make a non-idempotent op idempotent:**

| Technique | Mechanism | Best for |
|---|---|---|
| **Idempotency key** | Client sends `Idempotency-Key: <stable-id>`; server dedupes on it | Public APIs; payment APIs (Stripe, Adyen); any client-driven create |
| **Natural unique key** | Use a domain-stable ID (`order_id`, `external_event_id`) as the dedupe key | Internal services; webhook receivers |
| **Database unique constraint** | `UNIQUE INDEX` + `INSERT ... ON CONFLICT DO NOTHING` | Last line of defense; race-condition safety net |
| **Optimistic concurrency / version check** | `UPDATE ... WHERE version = ?` | Mutating-update safety |
| **State machine** | Transition only if not already in target state | Order/payment/job lifecycles |

**Idempotency key — the contract:**

| Aspect | Detail |
|---|---|
| Generated by | The **caller** (client / sender). The server receives it. |
| Format | UUID v4 / v7 / hash of `(resource_id, version)` — anything that's unique per logical request |
| Lifetime | Stored server-side with TTL (24–48 h is a common Stripe-style window) |
| Stored alongside | The **outcome** of the first call (status, response body) so retries return the same response |
| Conflict | Same key + different request body → reject (typically `409` or `422`) |
| Header convention | `Idempotency-Key: <key>` (not RFC, but de-facto standard) |

**Server-side handling pattern:**

```
on_request(key, request_body):
  txn:
    record = lookup(key)
    if record == null:
      result = perform(request_body)
      store(key, request_body_hash, result, expires_in=24h)
      return result
    elif record.body_hash == hash(request_body):
      return record.result      # idempotent retry
    else:
      raise IdempotencyConflict # same key, different body
```

| Step | Why |
|---|---|
| Wrap in a transaction | Prevent two concurrent retries from both processing |
| Hash the body | Detect "same key, different request" mistakes |
| Cache the response | Identical reply (including any generated IDs) on retry |
| TTL the entry | Free storage; after TTL, key can be reused |

**Two-direction idempotency — both sides need to agree:**

| Direction | Mechanism |
|---|---|
| **Outbound** (client retries) | Client sends `Idempotency-Key`; server dedupes |
| **Inbound** (server receives duplicates) | Dedupe on a unique field (event_id, message_id) inside a transaction |

> **Webhook receivers** are a classic example of "inbound" — providers (Stripe, GitHub) retry on non-2xx responses. Receivers must dedupe on the provider's `event_id`.

**Database-level dedupe patterns:**

```sql
-- Unique constraint + ON CONFLICT
CREATE UNIQUE INDEX idx_event_external_id ON events(external_id);
INSERT INTO events (external_id, payload, processed_at)
VALUES (?, ?, NOW())
ON CONFLICT (external_id) DO NOTHING;

-- Optimistic concurrency on stateful update
UPDATE accounts
   SET balance = balance - 100, version = version + 1
 WHERE id = ? AND version = ?;
-- 0 rows affected → someone else updated; reject or retry
```

**State-machine pattern (the safest for lifecycle ops):**

```
order.status: PENDING → PAID → SHIPPED → DELIVERED
                       ↑
                       │
              "mark_paid(order_id)" is idempotent
              because the transition only fires
              if status is currently PENDING.
```

| Property | Effect |
|---|---|
| Transitions are guarded by current state | Re-running `mark_paid` on a paid order is a no-op |
| Each event recorded once (event-sourcing-style) | Audit trail + replay |
| Combine with conditional update | Atomic "transition if currently in X" |

**At-least-once vs exactly-once:**

| Guarantee | Reality |
|---|---|
| **At-most-once** | Possible by not retrying — accept loss |
| **At-least-once** | Default in real distributed systems — duplicates possible |
| **Exactly-once delivery** | A common myth — impossible across arbitrary failures |
| **Exactly-once *processing*** | Achievable via at-least-once delivery + **idempotent consumers** |

> "Exactly-once" the systems community accepts is **at-least-once delivery + idempotent processing** — the duplicates arrive, the consumer makes them harmless. Kafka's "exactly-once semantics" means transactional producers + idempotent consumers, scoped to Kafka.

**Where idempotency is non-negotiable:**

| Surface | Why |
|---|---|
| Payment APIs | Double-charge = customer disaster |
| Order creation | Duplicate orders annoy users + costs |
| Email / SMS / push send | User receives 5 copies of the same message |
| Webhook receivers | Providers retry aggressively on non-2xx |
| Message queue consumers | At-least-once delivery → duplicates |
| Database migrations | Re-running a migration must not double-apply |
| Background job execution | Retries on worker failure |
| File / S3 uploads | Multipart resume / retry |
| External API calls (POST) | Network blip → "did it succeed?" — pair with idempotency key |

**Anti-patterns:**

| Anti-pattern | Why it bites |
|---|---|
| Server-generated keys | Client doesn't know the key on retry → can't dedupe |
| Storing only "this key was seen" without the response | Retry returns wrong / null result |
| No body-hash check | Same key reused for different request silently masks a bug |
| TTL too short | Legit retries past the window create duplicates |
| TTL too long | Storage growth; key collisions on UUID reuse |
| Using `INSERT ... ON CONFLICT DO UPDATE` when DO NOTHING is right | Last-writer-wins masks duplicates |
| Idempotency at the API but not the consumer | Half-protected — duplicates from queues still hit |
| Relative updates (`x = x + 1`) | Retries multiply the effect |
| `SELECT-then-INSERT` without a unique constraint | Race condition between check and insert |

**Designing for idempotency — checklist:**

| Question | If "no" → |
|---|---|
| Can a client safely retry this request? | Add an idempotency-key contract |
| Is the operation a state transition? | Guard with current-state check |
| Does the operation have a natural unique key (order_id, event_id)? | Use it; add a unique constraint |
| Is there a path where the same logical event arrives twice? | Dedupe at the consumer using the event's id |
| Does the operation use relative arithmetic? | Convert to absolute / version-checked update |
| Is there a timeout that triggers retry on the client? | Make the operation idempotent end-to-end |

**Cleanup of idempotency-key records:**

| Strategy | When |
|---|---|
| TTL (24–48 h typical) | Most public APIs |
| Hard-delete on success after observation window | Internal high-volume systems |
| Archive to cold storage | Audit / compliance requirements |
| Soft-delete (flag) | Need to detect very old retries |

**Rule of thumb:** **every API that mutates state should accept an `Idempotency-Key`** — caller-generated, server-stored with the response, TTL'd. **Every queue consumer should be idempotent**, deduping on the message / event id. Use **database unique constraints + `ON CONFLICT`** as the safety net under everything. Prefer **absolute updates** (`SET x = 5`) over **relative** (`x += 1`) wherever the domain allows. Don't claim "exactly-once delivery" — claim "at-least-once delivery + idempotent processing".
