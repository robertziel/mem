### Vector Databases — Embeddings & Similarity Search

**Definition:** **embeddings** are dense numerical vectors that represent the **meaning** of text / images / audio. Similar content → similar vectors (close in vector space). **Vector databases** store and search billions of vectors via **approximate nearest neighbor (ANN)** indexes (HNSW, IVF, PQ). Backbone of **RAG**, **semantic search**, **recommendations**, **clustering**.

**What embeddings do:**

| Concept | Detail |
|---|---|
| Dense vector | Float array, fixed dimensions |
| Distance ≈ semantic similarity | Closer in space = similar meaning |
| Generated by encoder model | LLM / sentence transformer / vision model |
| Same model on both sides | Query + corpus must use same encoder |
| Capture context | "Apple" the company vs the fruit (depending on training) |

**Embedding model characteristics:**

| Model | Dim | Speed | Quality |
|---|---|---|---|
| `text-embedding-3-small` (OpenAI) | 1536 | Fast | Good default |
| `text-embedding-3-large` (OpenAI) | 3072 | Slower | Best quality |
| `BAAI/bge-large-en` | 1024 | Fast | Strong open-source |
| `Cohere embed-v3` | 1024 | Fast | Multilingual |
| `gte-large` | 1024 | Fast | Open-source |
| `nomic-embed-text` | 768 | Fast | Tiny, OSS |
| Cross-encoder reranker | n/a | Slow | Most accurate |

**Dimension trade-off:**

| Dim | Pros | Cons |
|---|---|---|
| 384 (small) | Cheap, fast | Less expressive |
| 768 (medium) | Balanced | Standard |
| 1536 (default) | Strong baseline | More memory |
| 3072 (large) | Highest quality | 2× cost |
| **Matryoshka** | Truncate to 256 / 512 for coarse search, full for precise | Best of both |

**Similarity metrics:**

| Metric | Formula | When to use |
|---|---|---|
| **Cosine similarity** | `dot(A,B) / (‖A‖·‖B‖)` | Most common — direction matters, not magnitude |
| **Euclidean (L2)** | `√Σ(aᵢ−bᵢ)²` | When magnitude matters |
| **Dot product** | `Σ(aᵢ·bᵢ)` | When already normalized |
| Manhattan (L1) | `Σ|aᵢ−bᵢ|` | Rare for embeddings |

> **Default to cosine similarity** with normalized embeddings. Most modern embedding models produce normalized vectors, so dot product = cosine.

**Vector databases — the landscape:**

| Database | Type | Best for |
|---|---|---|
| **Pinecone** | Managed SaaS | Easiest, fully managed |
| **pgvector** | Postgres extension | Already on Postgres, < 100M vectors |
| **Weaviate** | OSS, self-hosted | Hybrid search, rich features |
| **Qdrant** | OSS, Rust | High perf, filtering |
| **Chroma** | OSS, lightweight | Prototyping, embedded |
| **Milvus** | OSS, distributed | Large scale, production |
| **FAISS** | Library (not a DB) | In-memory similarity search |
| **Vespa** | OSS, Java | Hybrid search + ranking |
| **OpenSearch / Elasticsearch** | Hybrid search | Combine vector + BM25 |
| **Redis** (with RediSearch) | KV + vector | Mixed workload |

**pgvector — Postgres-based vector search:**

```sql
CREATE EXTENSION vector;

CREATE TABLE documents (
  id           SERIAL PRIMARY KEY,
  content      TEXT,
  embedding    vector(1536),
  metadata     JSONB
);

-- IVF index (faster build, lower recall)
CREATE INDEX ON documents
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);

-- HNSW index (best recall, more memory)
CREATE INDEX ON documents
USING hnsw (embedding vector_cosine_ops);

-- Query: find top-5 similar
SELECT content, 1 - (embedding <=> $1) AS similarity
FROM documents
ORDER BY embedding <=> $1   -- <=> is cosine distance
LIMIT 5;

-- With metadata filter
SELECT content, 1 - (embedding <=> $1) AS similarity
FROM documents
WHERE metadata->>'doc_type' = 'spec'
ORDER BY embedding <=> $1
LIMIT 5;
```

**ANN (Approximate Nearest Neighbor) index types:**

| Index | How | Trade-off |
|---|---|---|
| **Flat / brute force** | Compare with every vector | Exact, slow at scale |
| **IVF** (Inverted File) | Cluster vectors, search nearest clusters | Fast, some recall loss |
| **HNSW** (Hierarchical Navigable Small World) | Graph-based navigation | **Best recall**, more memory |
| **PQ** (Product Quantization) | Compress vectors | Low memory, lower accuracy |
| **IVF + PQ** | Combine | Memory-efficient, good recall |
| **DiskANN** | On-disk graph | Massive scale |
| **ScaNN** (Google) | Quantized + asymmetric distance | High perf |

**HNSW vs IVF — most common pick:**

| Property | HNSW | IVF |
|---|---|---|
| Recall | **Higher** (90%+ typical) | Slightly lower |
| Memory | Higher | Lower |
| Build time | Slower | Faster |
| Query time | Very fast | Fast |
| Tuning params | `M`, `ef_construction`, `ef_search` | `lists`, `nprobe` |
| Best for | Most production cases | Memory-constrained |

**Quantization (reduce storage / cost):**

| Method | Compression | Quality loss |
|---|---|---|
| **Scalar quantization** (float32 → int8) | 4× | Minimal |
| **Binary quantization** (1 bit per dim) | 32× | Some |
| **Product quantization** | Variable | Tunable |
| **Matryoshka** (dimension truncation) | 2–6× | Variable |

**Hybrid search — vector + keyword:**

| Component | Detail |
|---|---|
| Dense (vector) | Captures semantic meaning |
| Sparse (BM25) | Catches exact keywords (names, IDs) |
| Combine via | RRF (Reciprocal Rank Fusion) or weighted score |
| Tools native to hybrid | Weaviate, Vespa, OpenSearch, Pinecone |
| Better recall + precision | Almost always wins over pure dense |

**Common queries:**

| Query | Use case |
|---|---|
| "find K most similar" | Document retrieval, RAG |
| "find similar within filter" | Multi-tenant, permissions |
| "find similar within distance threshold" | Quality cutoff |
| "find candidates for clustering" | Topic detection |
| "diverse top K" | Recommendation diversity (MMR) |
| "deduplicate near-duplicates" | Content moderation |

**Common patterns:**

| Pattern | Detail |
|---|---|
| **RAG retrieval** | Embed question → ANN search → top-K to LLM |
| **Semantic search** | Replace keyword search with embedding similarity |
| **Recommendation** | Item-item ANN; user embedding → item ANN |
| **Image search** | CLIP embeddings + ANN |
| **Clustering / topic detection** | Group similar embeddings |
| **Dedup** | Find near-duplicates |
| **Anomaly detection** | Distance to nearest cluster |

**Multi-tenancy + permissions:**

| Pattern | Detail |
|---|---|
| Metadata filter | `WHERE tenant_id = ?` before/after ANN |
| Per-tenant index | Stronger isolation but more ops |
| Pre-filter (HNSW + metadata) | Tools vary in support |
| Post-filter (search then filter) | May lose results |
| Blast-radius mistakes | Rigorous testing |

**Cost factors:**

| Factor | Detail |
|---|---|
| Index memory | HNSW + 1536-dim ≈ 6 KB / vector |
| Embedding generation | $/M tokens at API or GPU-hour |
| Query rate | Concurrent queries = capacity |
| Storage at rest | Per-vector + metadata |
| Re-embedding when model changes | Significant migration |

**Common pitfalls:**

| Pitfall | Effect |
|---|---|
| Using different embedding models for query and corpus | Misaligned space |
| Forgetting normalization | Wrong cosine results |
| No metadata filtering | Cross-tenant leak |
| Index without tuning | Poor recall |
| Building HNSW on huge corpus without sharding | OOM |
| Treating ANN result as exact | Some false negatives |
| Not eval'ing recall | Don't know quality |
| Over-paying for managed vector DB | pgvector might suffice |
| Storing huge JSON metadata in vector DB | Use external store |

**Migration / re-embedding:**

| Trigger | Strategy |
|---|---|
| Better embedding model released | Re-embed all corpus, A/B test |
| Schema change | Background re-index |
| Quality drop | Often the embedding model, not the DB |

**Evaluation metrics:**

| Metric | What |
|---|---|
| **Recall @ K** | Of true relevant items, how many are in top-K? |
| **Precision @ K** | Of top-K, how many are relevant? |
| **NDCG @ K** | Quality of ranking |
| **Latency p99** | Operational |
| **Throughput** | Queries / second |
| **Index build time** | Operational |

**Decision matrix:**

| Need | Pick |
|---|---|
| Already on Postgres, < 100M vectors | **pgvector** |
| Managed, easiest | **Pinecone** |
| OSS, hybrid search | **Weaviate** |
| OSS, performance-critical | **Qdrant** |
| Embedded / dev | **Chroma** |
| Distributed billions | **Milvus** |
| Add to existing search | OpenSearch / Vespa |
| Pure in-memory library | FAISS |

**Rule of thumb:** **pgvector** if you're already on Postgres and have < 100M vectors. **Pinecone** for managed production. **HNSW index** for best recall (most cases). Start with **cosine similarity** on normalized embeddings. **Quantize** for cost at scale (binary or scalar). The **embedding model choice matters more than the vector DB choice** — invest there first.
